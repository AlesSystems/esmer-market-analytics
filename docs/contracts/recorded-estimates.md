## Capability and scope

The owner can view offline product/day/month estimates from a declared isolated backup window. Source meanings remain unverified. The quality is always `unverified-estimate`; reviewing, exporting or reconciling the arithmetic cannot promote it. Financial `SalesReports`, operating results and accepted monthly reports keep their existing contracts.

The new `sql-backup-estimate-v1` package has the same restricted raw fields as `sql-backup-preview-v1`, plus exactly `BELGE_TARIHINDEKI_SON_ALIS_FIYATI` on each line. Its value is a decimal string or null. The old package version rejects this extra field and remains readable unchanged. Both versions retain `isolated-sql-backup` provenance and `sourceReconciled:false`. These two versions add no names, supplier/customer/employee fields or arbitrary evidence text.

On 2026-10-22 the owner approved [#99](https://github.com/AlesSystems/esmer-market-analytics/issues/99): a new estimate package schema version may add read-only product name, product group/category name and unit code (if available) from the `STOK` master. The #99 preparation allowlist (`tools/prepare-sql-backup.ts`, with raw-package exact-column checks) defines the exact raw columns after catalog review. No supplier or customer columns are added. Older packages still open and display `Ürün #<ID>`. See the [privacy allowance](privacy.md#product-catalogue-columns-99).

The initial real package reuses the previously reconciled September 2025 private extraction. That reuse needed no renewed SQL read or grant change. Later packages come from `npm run prepare:month`. With owner approval on 2026-10-22, recorded in [#101](https://github.com/AlesSystems/esmer-market-analytics/issues/101), that command reads the cost candidate directly. It reads only from an isolated restored copy, never from the live connection, and uses the exact projection in the [privacy allowance](privacy.md#recorded-estimate-package-allowance). The preparation step proves exact header/line identity and operand agreement with the retained preview before adding the cost candidate. An import validates canonical bytes, hashes, references, dates, row/byte bounds and exact columns before atomic replacement. Invalid imports preserve current data.

## Fixed population and formulas

The selected calendar month uses the recorded date substring from `FIS_TARIHI`. This is an assumption about business dates, not a timezone conversion or validated event timestamp. Only overlap with the declared extraction range is observable. Days outside that range are gaps. An empty observed day means no eligible recorded rows, not proof of no sales.

Sale candidates require header `FIS_TURU=11`, `CURRENCY=TRY`, `DURUM=1` and `AKTIF=1`. These flags select candidates but do not prove completed sales. Type 35 remains excluded because economic identity relative to type 11 is unproved. Other types, currencies and statuses are excluded and counted. Each excluded line receives one primary reason, in this order: type 35, other type, unsupported currency, unsupported status, missing/negative amount, unattributed return cost, invalid quantity, unsupported multiplier, missing cost, zero cost, negative cost. Covered lines have no exclusion reason. Counts partition the full period line population. Empty headers have a separate document count and unknown exposure; do not add document counts to line counts. No foreign-currency conversion occurs.

The revenue operand is nonnegative, nonnull `TOPLAM_KDV_MATRAHI`. It is an assumed recorded amount basis. Do not label it verified revenue or KDV-exclusive net sales. Do not allocate additional discounts or taxes. Invalid or missing amounts have unknown exposure, never zero exposure. Candidate sale and return amount totals are null when no valid known operands exist. If known and unknown operands coexist, display the known subtotal with the unknown-amount count. A known zero operand may produce a calculated zero. No candidate rows means unavailable amount, with the separate zero row count explaining why.

Cost-covered sale candidates additionally need positive `MIKTAR_FIS`, `CARPAN` numerically equal to one, and a strictly positive historical-cost candidate. Their candidate cost is quantity times that field. Their contribution is recorded amount minus candidate cost. These rules assume the operands share unit and tax basis; they do not prove transaction-time costing. Null, undocumented zero and negative cost are distinct exclusions. No current-price fallback occurs. Unknown/nonunit multiplier and invalid quantity exclude cost coverage.

Type 12 with the same currency/status/date selection contributes a separate nonpositive candidate return amount, subtracting a nonnegative recorded amount exactly once. Every return's cost and contribution remain excluded because original-sale attribution is unavailable. Return exposure appears in Rapor, and the page trust chip explains that the covered contribution omits their economic effect and can overstate the result. Do not subtract return revenue from contribution while implicitly assigning zero cost.

The headline is covered sale contribution. It is null when no covered sale lines exist. A calculated zero or negative contribution remains a valid displayed amount. Candidate sale amounts, candidate return amounts, covered sale amounts, candidate costs and contribution remain distinct. The report never claims whole-market profit.

Product, day and monthly totals partition the same eligible recorded lines. Product identity remains its exact source ID. Packages with #99 catalogue columns display the product name; older packages and missing names fall back to `Ürün #<ID>`. The group name allows category rollups over the same partition. The unit code is a label only: kg and adet are never summed together into a physical total, and no cross-unit quantity claim is displayed. Costs can vary by line within a product. Exact product-ID lookup and paging never change summary or daily scope. The real September window contains 3,529 product IDs, so lookup must search the full result rather than only the visible page.

Use decimal precision 200 for this version. The raw operand bound is 40 integer and 30 fractional digits, so a product of two operands and at most 100,000 rows fits this precision. Money strings retain exact digits; no cent tolerance or raw-source rounding rule is invented. Percentages may round to two places for display and never feed amounts. Cost coverage uses absolute candidate sale plus return amount as denominator, covered sale amount as numerator, and null for a zero denominator. If that denominator is positive but no lines have cost coverage, the percentage is zero while covered money and contribution remain null. Unknown-amount rows remain explicit even when a displayed percentage reaches 100.

## Owner-facing terms

Primary screens use plain Turkish terms. The formulas above are unchanged.

- *Satış* is the candidate sale amount.
- *Tahmini brüt kâr* is the covered sale contribution.
- *Marj* is Tahmini brüt kâr ÷ covered sale amount over the same population. It is null when the covered sale amount is ≤ 0 or no covered lines exist. Display may round it to two decimals; the rounded value never feeds amounts.
- *Tahmini net kâr* is Tahmini brüt kâr minus the month's expenses that the owner entered and marked complete, counted under the [expense contract](expense-completeness.md#operating-result)'s classification and KDV-treatment rules: excluded classifications (asset purchases, taxes, financing, owner contribution/withdrawal, transfers) stay out, and unknown treatment or nonzero unclassified values withhold the figure. If the month's expenses are not marked complete, no net figure is shown and the existing missing-expenses message remains. It inherits the estimate's limits and is not the validated operating result.

Primary screens do not use *katkı*, *aday*, *kapsanan* or source codes. These may remain in Rapor method details, export and internal identifiers. Calling the estimate *kâr* is allowed; calling the amount basis verified revenue is not.

## Visible limits and provenance

The monthly view shows one trust chip per page, for example "Tahmini kâr · maliyeti bilinen satış %98,3", where the percentage is the cost coverage above. It opens a short explanation: estimate basis, excluded costs, returns not netted out of kâr, and unknown amounts. Detailed included/excluded counts, missing/zero/negative-cost reasons, return exposure and method details are in Rapor. Null or unknown values are never drawn or shown as zero; unknown amounts use hatched marks. A valid zero and a loss stay distinct. Missing, zero or negative cost never becomes zero. Method details contain the fixed assumption version, source package hash, extraction window and date. All required assumptions remain available in Turkish. The user cannot turn off or edit the versioned formula through free-form package fields.

Every query and export pins source hash and period. A replaced package causes a stale response, never mixed months or old product detail under new totals. The service returns bounded product/evidence pages. The service does all financial arithmetic with deterministic decimal precision 200; the renderer performs none. Each query also returns a `ranking` of at most ten products by contribution, descending, with product ID ascending as tie-break. Products without covered lines have unknown contribution and are left out rather than ranked as zero. The ranking is separate from the ID-ordered product pages and does not change the request payload. Each total also carries the service-computed `uncoveredSaleAmount`: candidate sale minus covered sale, or null when no candidate sale amount is known. When any sale line has an unknown amount it is only the known subtotal, never a complete figure. Charts use it to show sales without cost coverage and mark such days with a hatched "Tutarı bilinmeyen satış" segment; a known return subtotal with unknown return amounts keeps a hatched stub below the return bar, and the day table lists the unknown-amount row count. The Excel export does not include it. Raw document drilldown stays available.

Excel contains every product and day for the selected report, plus method, assumptions, scope and exclusions. Every sheet identifies the result as unverified and records the same source hash and calculation version. Values that Excel cannot represent exactly remain text. No spreadsheet formula recomputes profit.

V1 estimates are transient. They do not have accepted financial-report versions. The current source package survives restart and encrypted backup/recovery. Export preserves an estimate outside the app, while a later source import replaces the in-app estimate. Existing saved financial reports and app-owned expenses/settings remain unchanged.

## Month profit view (#102, #106)

`readMonthProfit({month:"YYYY-MM"})` is the single named IPC read for the profit-first pages. The payload has exactly the key `month`; the sender, operation and payload are validated before the service runs. The service (`src/source/month-profit.ts`, `month-profit-v1`) builds `MonthProfitView` from `calculateSourceEstimate` and does not change any formula above.

- **Availability.** Only an active `sql-backup-estimate-v1`/`-v2` package feeds it. No package or a preview-only package returns `{status:"source-unavailable",code:"ESTIMATE_UNAVAILABLE"}`. A month that does not overlap the extraction window returns `code:"MONTH_NOT_COVERED"`. Neither case returns zeros. `dataFrom` is the later of the window start and the month's first day; `dataUntil` is the earlier of the window end and the month's last day. Parsed packages and per-month estimates are cached per package hash and dropped on replacement.
- **Totals.** `sales` = candidate sale amount, null when no sale amount is known; `knownCostSales` = covered sale amount; `cost` = candidate cost and `grossProfit` = contribution, both null when no line has a known cost (never `"0"`); `marginPct` = grossProfit ÷ knownCostSales × 100, null when grossProfit is null or knownCostSales ≤ 0; `costKnownPct` = the existing cost-coverage percentage, whose denominator is sales plus the absolute return amount, so returns lower it; `unknownCostSales` = uncovered sale amount; `unknownCostProducts` = products with a sale line excluded for quantity, multiplier or missing/zero/negative cost. `returns` is the positive return amount, null when no return amount is known, shown separately and never subtracted from profit. `unknownSaleAmounts` and `unknownReturnAmounts` count lines whose recorded amount is missing or negative; those lines are in neither sum. `receipts` = distinct sale documents with a known amount; `averageBasket` = sales ÷ receipts, null without receipts.
- **Rounding.** Amounts keep full decimal precision 200. Divisions are rounded half-up to two places for transport: percentages (always two decimals), `averageBasket`, `unitPrice` and `unitCost`. Thresholds compare unrounded values (a 1.495-point drop is not flagged; a 7.995 % margin, shown as 8.00, is under 8), and rounded values never feed amounts.
- **Previous and history.** `previous` is the previous calendar month's totals from the same package, or null when the window does not cover it. `history` lists up to six months ending at `month`, ascending, covered months only.
- **Changes (#103).** `changes` compares `totals` with `previous` and is null when `previous` is null. `salesPct`, `grossProfitPct` and `netProfitPct` are (current − previous) ÷ previous × 100, null when either side is null or the previous value is not positive, and also null when the current or the previous month is only partly loaded (a partial month is not comparable in amounts; the UI shows no comparison, never 0). `marginPoints` is the current margin minus the previous margin, computed from unrounded margins (grossProfit ÷ knownCostSales × 100) and then rounded once, null when either margin is null. `marginPoints` is a ratio and stays comparable for partial months. All four are rounded half-up to two places. The renderer shows them as they are and does no arithmetic of its own.
- **Products.** Products with at least one sale candidate line, sorted by sales descending, then numeric ID. `cost`, `grossProfit` and `marginPct` are null without covered lines. `quantity`, `unitPrice` and `unitCost` use cost-covered lines only and are null when the unit is unknown, so kg and adet are never mixed across products. `previousMarginPct` and per-month `history` margins are null where not computable. `marginChangePoints` = marginPct − previousMarginPct in points, from unrounded margins, null when either is unknown. `unitProfit` = grossProfit ÷ quantity over the same cost-covered lines, null without quantity or cost. `profitSharePct` = grossProfit ÷ the month's grossProfit × 100, null when either is unknown or the month's grossProfit ≤ 0. `profitRank` = 1-based position by grossProfit descending (ties by numeric ID), null when grossProfit is unknown. `flags` decide Ürünler's quick filters on unrounded values: `loss` (margin < 0), `lowMargin10` (margin < 10 %), `marginDrop` and `missingCost` (the attention rules below). An unknown margin sets none of loss, lowMargin10 or marginDrop. The per-100 ₺ figure on the product card is `marginPct` itself; divisions round to 2 places, ROUND_HALF_UP.
- **Categories.** Grouped by the #99 category name; products without a category are left out. Margin uses the same covered population. Sorted by sales descending, then Turkish name order.
- **Attention.** Literal thresholds: `loss` when margin < 0; `marginDrop` when margin fell by ≥ 1.5 percentage points against the previous month; `lowMarginHighVolume` when a product is in the top five by sales and margin < 8 %; `missingCost` when a sale line was excluded for a cost reason. Order is by kind in that sequence, then by product sales rank.
- **Net profit.** `expenses` is the month's counted expense total under the [expense contract](expense-completeness.md#operating-result) (recoverable KDV counts net, otherwise gross; excluded classifications stay out). It is null when a component blocks it or nothing has been entered. `netProfit` = grossProfit − expenses only when the month's completeness confirmation is current and no component blocks it. Otherwise it is null with `netProfitReason`, the first that applies: `costUnknown` (grossProfit is null), `monthPartial` (the package window does not cover the whole calendar month at the start or the end, matching `periodCoverageComplete` in the validated reports), `unknownTax` (an expense has unknown KDV treatment or no tax evidence), `confirmationStale` (an expense revision after the confirmation), `expensesMissing` (nothing entered and not confirmed) or `expensesIncomplete` (not confirmed, or unclassified/loss/legacy review pending). Only aggregate labour is read.

## Acceptance

Independent synthetic golden amounts and a separate Python Decimal calculation over the retained real operands must match all product/day/month values and exclusions exactly. Real arithmetic reconciliation proves the declared formula, not the source assumptions. Private amounts and source IDs stay outside Git, logs and screenshots.

Checks cover old/new package validation, same/replacement/corrupt/cancelled import, stale requests, null/zero/loss/returns-only, exact decimal boundaries, full export beyond pagination, encrypted recovery, packaged import/reopen/drilldown/export, keyboard and zoom. Relevant full suites, lint, typecheck and build run before publication. Windows acceptance for v1 is the single deferred Windows smoke test in [#109](https://github.com/AlesSystems/esmer-market-analytics/issues/109). This decision does not change the 100,000-row bound; the 2 s benchmark applies only if prepared packages exceed 100,000 rows (#98 gate 6). Production POS access and owner installation are separate.
