## Raw route and practical estimate seam

`src/source/raw-package.ts:RawPackage` is `sql-backup-preview-v1`, provenance isolated-sql-backup and `sourceReconciled:false`. Exact header/line allowlists and decimal strings are validated. Current line allowlist has no cost and no physical unit. `src/store/store.ts:importSourcePreview` atomically replaces a singleton separately from financial datasets. `querySourceWorkspace` verifies its bytes/hash then calls `src/source/workspace.ts:querySource`; request.hash prevents mixing replaced data. `readSourcePreview` returns50 rows. Raw preview already participates in encrypted recovery via `src/recovery/validate.ts:readRawPackage` and hash validation.

`src/ui/App.tsx` prefers the source workspace after preview import. `src/ui/SourceWorkspace.tsx` owns period/navigation and source hash, and currently shows record counts on monthly screen. This is the narrowest entry for a separate **unverified source estimate**. Add a service-side pure aggregate capability over a validated raw estimate package; return an independently typed summary/day/product result and bounded pages. Keep `SalesReports.open` unchanged and retain raw-source drilldown. Reuse Exact/money/percent, existing IPC sender/payload checks, service jobs, hash staleness and page controls. Do not cast raw estimates into SalesComponent, GrossResult or MonthlyReportV2.

An explicit capability/package version can carry the approved candidate historical-cost field without silently widening old v1 validation. Assumptions must be data, retained in export: type11 candidate sales, type12 signed candidate return amounts with cost excluded, type35 excluded, status/currency/date rules, candidate cost basis, CARPAN=1 restriction, no physical-unit assertion. These are root design inputs, not independently validated business meanings. Unknown/missing/negative/undocumented-zero cost stays null; returns exclusion appears next to total, since ignoring their cost can distort the contribution. Display raw recorded quantity per product without summing incompatible units. Candidate basis label must avoid claiming KDV-exclusive net sales or transaction-time cost.

## Saved-report and compatibility constraint

`src/reports/versions.ts:ReportVersions.resolve` recognizes only monthly-report-v1/v2, pins candidate/accepted evidence, and compares same period/lineage/filters. `accept` stores immutable output/review but review never verifies economics. `src/store/store.ts:acceptReport` calls `snapshot(pin)`; a nonnull datasetId must exist in datasets. Raw package hashes are not dataset IDs, and singleton replacement destroys old raw package availability unless retained elsewhere. `listMonthlyReports` hardcodes the two format names.

`src/recovery/validate.ts:validateProductProfit` independently checks source pin/component equality, historical cost provenance, all scopes, statuses, dates, memberships, warnings and totals. It rejects other monthly-report-* formats. Reusing existing monthly types by weakening these invariants would invalidate trusted synthetic/history meaning. Small V1 option: transient pinned estimate plus Excel export, raw package retained in recovery; leave financial saved versions untouched. If estimate saving is required, define its separate format and pin/source evidence retention/validator first, then add history/display/compare deliberately. Generic AcceptedReport.output storage alone is not sufficient validation.

`src/reports/export.ts:excelReport` exports all full report values, not product pagination, preserving exact decimal text when Excel cannot retain15-digit precision, and rejects sheet/cell size limits. Reuse those numeric/table primitives or their convention in a separate estimate export. Every estimate sheet needs assumption/confidence/sourcehash metadata; exported title must stay unverified. Avoid a second arithmetic implementation inside Excel or UI.
